# Sorting Visualizer

**정렬 알고리즘 58종이 어떻게 움직이는지 눈과 귀로 확인하는 웹앱**

🔗 https://sort-algo-psi.vercel.app

## 소개

버블·퀵 같은 익숙한 정렬부터 그레일 정렬 같은 보기 드문 정렬까지, 58가지 정렬 알고리즘을 시각화합니다. 막대의 움직임뿐 아니라 실행 중인 코드 줄과 줄별 실행 횟수, 정렬이 내부에서 쓰는 힙·트리·버킷까지 보여 주어 "알고리즘이 지금 무엇을 하는지" 이해하는 데 초점을 맞췄습니다. 두 알고리즘을 같은 입력으로 나란히 비교할 수도 있습니다.

## 주요 기능

- **재생 제어**: 재생/일시정지, 한 단계 앞·뒤, 진행바 드래그, 속도 ×0.25 ~ ×1024
- **비교 모드**: 같은 배열로 두 알고리즘을 나란히 돌리고 비교·교환·이동 횟수 비교, 먼저 끝난 쪽 표시
- **데이터**: 크기 2~1000, 프리셋(무작위 순열/중복 있음/거의 정렬됨/역순/중복 많음), 직접 입력(0~9999)
- **학습용 정보**: 시간·공간 복잡도, 안정성, 설명용 구현 코드
- **코드 줄 하이라이트**: 재생 중 지금 실행 중인 코드 줄을 강조하고 줄별 실행 횟수를 히트맵으로 표시 (58종 전체)
- **구조 보기**: 막대 대신 정렬이 쓰는 구조를 그림 (패널의 "막대 | 트리·더미·칸" 전환)
  - 트리: 힙 정렬·상향식 힙·3진 힙(배열 = 힙), 트리 정렬(이진 검색 트리), 스플레이 정렬(넣을 때마다 루트로 끌어올리는 회전), 카테시안 트리 정렬(트리 만들기 → 최소 힙으로 꺼내기), 토너먼트 정렬(대진표)
  - 더미: 페이션스 정렬의 카드 더미
  - 칸: 버킷 정렬의 버킷(슬롯별 버킷 수 반영), 계수 정렬의 값별 칸, 기수 정렬의 자릿수별 0~9 칸
- **정렬 소리**: 강조된 막대의 값을 음 높이로 들려줌 (비교·교환·읽기마다 음색이 다르고, 완료되면 올라가는 효과음, 비교 모드는 좌우로 나눠 재생하고 한쪽만 음소거 가능). 기본값은 꺼짐
- **공유**: 현재 설정(알고리즘, 속도, 크기, 커스텀 배열 등)이 URL에 반영됨
- **테마**: 밝은·어두운 테마 (처음에는 OS 설정을 따르고, 제목 옆 버튼으로 전환)
- **단축키**: `Space` 재생/일시정지 · `←` `→` 한 단계 · `R` 새 배열 · `M` 소리 켜기/끄기

## 기술적으로 신경 쓴 점

### 1. 연산 로그 기반 재생 엔진

- 단계마다 배열을 복사해 저장하던 방식을 연산 로그로 바꿨습니다. 알고리즘이 `cmp / swap / move / mark`를 호출하면 `[종류, a, b, 줄]` 숫자 4개만 기록하고, 이를 `Int32Array`로 압축합니다.
- 모든 연산에 역연산이 있어서, 과거 상태를 저장하지 않고도 되감기와 진행바 이동이 됩니다.
- 퀵·병합 1,000개 기준 메모리가 134~143MB에서 0.3~0.4MB로 줄었습니다. 예전 방식은 버블 정렬 1,000개에서 메모리가 4GB를 넘었습니다.

### 2. 메인 스레드를 막지 않는 구조

- 정렬 계산은 Web Worker에서 하고, 결과 버퍼는 복사 없이 소유권만 넘깁니다(transfer).
- 워커는 화면이 열릴 때 미리 띄워 두고 재사용합니다. 재생할 때마다 새로 띄우던 기동 비용을 없애 100개 기준 재생 시작이 47.9ms에서 32.2ms로 줄었습니다(중앙값).
- 재생은 `requestAnimationFrame` 누적기로 한 프레임에 여러 연산을 처리하고, 100개를 넘으면 DOM 대신 canvas로 그립니다.
- 그 결과 예전 버전에서 약 7.5초 멈추던 클릭(버블 정렬 1,000개)이 8ms가 됐습니다. 1,000개 비교 모드도 1024배속에서 초당 약 1만 단계를 60fps로 재생합니다.

### 3. 화면과 코드가 어긋나지 않게 하는 테스트

- 설명용 코드 줄 끝에 `//@cmp` 같은 표식을 달고, 실제 기록된 연산이 그 줄의 종류와 맞는지 자동으로 검사합니다.
- 알고리즘마다 공통 테스트(정렬 결과, 원소 보존, 재생 일치, 안정성)와 알고리즘별 특성 테스트를 두었습니다. 예를 들어 머지-삽입 정렬의 비교 횟수가 이론상 최솟값 이하인지 확인합니다.
- PR마다 GitHub Actions로 lint·타입 체크·테스트를 실행합니다.

### 4. 원래 정의에 충실한 구현

- 블록 정렬(WikiSort)과 그레일 정렬(GrailSort)은 보조 메모리 O(1)짜리 원본 알고리즘대로 구현했습니다.
- 보고보고 정렬은 원래 정의를 따라 다시 구현했습니다.
- 페어와이즈 정렬 네트워크는 0-1 원리로 검증했습니다.

## 구조 (Feature-Sliced Design)

```
src/
├─ app/                     Next.js 라우팅 + 전역 스타일 (FSD app 레이어)
├─ views/home/              페이지 조립, URL 상태, 단축키 (FSD pages 레이어 — Next의 pages/와 충돌하지 않게 views로 명명)
├─ widgets/visualizer/      막대 패널 + 지표 + 범례
├─ features/
│  ├─ playback/             재생 엔진(Track, useSortPlayer) + 재생바 UI
│  ├─ select-algorithm/     알고리즘 선택, 셸/버킷 옵션
│  ├─ sort-sound/           Web Audio 정렬 소리
│  └─ configure-array/      크기·프리셋·직접 입력
├─ entities/
│  ├─ sort-algorithm/       Op 로그, Tracer(연산 한도 300만), 알고리즘 58종(+테스트), 레지스트리·검색, 정보 카드, 코드 뷰어
│  └─ array/                배열 생성·파싱·검증, 막대 UI(DOM / canvas)
└─ shared/                  공용 타입, 유틸, UI
```

각 슬라이스는 `index.ts`로만 외부에 공개하고, 의존은 위 레이어 → 아래 레이어 한 방향으로만 흐릅니다.

## 동작 방식

알고리즘은 배열을 직접 다루지 않고 `Tracer`를 통해 `cmp(i, j)`, `swap(i, j)`, `move(from, to)`, `mark(i)`를 호출합니다. 호출은 `[type, a, b, …]` 형태의 연산 로그로 기록되고, 재생 엔진이 이 로그를 앞뒤로 적용합니다. 모든 연산에는 역연산이 있어서 되감기와 진행바 드래그가 가능합니다. 배열 스냅샷을 저장하지 않으므로 1000개 배열도 메모리 부담이 작습니다.

### 알고리즘 추가하기

1. `src/entities/sort-algorithm/algorithms/xxxSort.ts`에 `SortAlgorithm` 객체를 작성합니다.
   - 설명 코드는 `defineCode()`로 만들고, 연산이 일어나는 줄 끝에 `//@cmp`, `//@swap-root` 같은 표식을 붙입니다. 표식 이름은 `cmp*`(비교), `swap*`(교환), `move*`(이동), `read*`(읽기) 중 하나로 시작해야 합니다.
   - 구현에서 연산을 기록할 때 그 줄 번호를 함께 넘깁니다. 예: `t.cmp(i, j, CODE.line("cmp"))`
   - 설명 코드는 실제 기록 방식과 똑같이 동작하는 실행 가능한 JS여야 합니다.
2. `model/registry.ts`의 `ALGORITHMS`에 추가합니다.
3. `xxxSort.test.ts`에서 `describeSortAlgorithm(xxxSort)`를 호출합니다. 정렬 결과, id 보존, 연산 재생 일치를 확인하고, `stable: true`이면 안정성도 확인합니다.
   - `model/traced-code.test.ts`는 모든 연산에 줄이 붙어 있는지, 줄의 표식 종류가 연산 종류와 맞는지, 모든 표식이 실행되는지를 자동으로 검사합니다.

개발 과정의 문제와 해결 기록은 [DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)에 있습니다.
