## 1. 구조적인 문제

문제의 뿌리는 두 가지였다. **단계마다 배열 전체를 복사해 저장하는 데이터 모델**과 **700줄짜리 컴포넌트 하나에 모든 것을 몰아넣은 구조**.

### 1-1. 단계마다 배열 전체를 스냅샷으로 저장

```ts
// src/types/sort.ts
type SortStep = { array: ArrayItem[]; compare?: [number, number]; swap?: [number, number] };

// src/algorithms/bubbleSort.ts — 비교 한 번, 교환 한 번마다 배열을 통째로 복사
steps.push({ array: [...a], compare: [j, j + 1] });
```

- 메모리가 **단계 수 × 배열 크기**로 커진다. 1,000개 버블 정렬은 약 75만 단계 × 1,000개.
- 과거 상태를 되돌리는 방법이 없어 "한 단계 뒤로"나 진행바 이동을 만들려면 모든 스냅샷을 들고 있어야 한다.

### 1-2. 계산·재생·렌더가 모두 메인 스레드에서 한 단계씩

```ts
const start = () => {
  const s = getSteps(selectedAlgo, array);                 // 전체 단계를 동기로 한 번에 계산
  if (isCompareMode) s2 = getSteps(selectedAlgo2, array);  // 비교 모드면 한 번 더
  ...
};

const timer = setTimeout(() => {
  setArray(step.array);                 // 한 단계 = 한 번의 상태 변경 = 컴포넌트 전체 리렌더
  setStepIndex((prev) => prev + 1);
}, BASE_ANIMATION_SPEED / speedMultiplier);   // 100ms / 배속, 최대 16배
```

- 재생 버튼을 누르면 계산이 끝날 때까지 화면이 멈춘다.
- 한 프레임에 한 단계만 처리하므로 배속에 상한(16배)이 있고, 그마저도 렌더 비용 때문에 다 나오지 않는다.

### 1-3. 막대를 항상 DOM으로 그림

```tsx
// src/components/ArrayBars.tsx
<motion.div layout={!isLargeDataset} className="... bg-linear-to-t ... shadow-[0_0_15px_rgba(...)]" />
```

1,000개면 framer-motion 요소 1,000개(비교 모드는 2,000개)를 단계마다 갱신한다. 그라데이션과 그림자 때문에 비용이 더 크다.

### 1-4. 700줄짜리 컴포넌트 하나 (`src/components/SortVisualizer.tsx`)

- 상태, URL 동기화, 배열 생성, 재생 루프, 알고리즘 선택, 실행 시간, 코드 보기가 한 파일에 있다. `useState`만 20개가 넘는다.
- **비교 모드는 상태를 복붙했다.** `array`/`array2`, `steps`/`steps2`, `stepIndex`/`stepIndex2`, `executionTime`/`executionTime2`처럼 짝을 이루고, 재생 로직도 "알고리즘 1 진행"과 "알고리즘 2 진행"을 거의 같은 코드로 두 번 쓴다.
- 알고리즘 옵션(`shellGaps`, `bucketCount`)은 상태에 하나뿐이라 슬롯마다 다르게 줄 수 없다.

### 1-5. 알고리즘 하나를 추가할 때 고칠 곳이 4군데

1. `src/algorithms/xxxSort.ts`: 구현
2. `SortVisualizer.tsx`: import + `getSteps()`의 `switch`에 `case` 추가
3. `ControlPanel.tsx`: `ALGORITHMS` 목록(이름·설명)
4. `src/data/algoCode.ts`: 화면에 보여 줄 설명 코드

하나라도 빠뜨리면 목록에는 있는데 실행되지 않거나(`default: return []`) 코드가 비어 보인다.

### 1-6. 화면에 보여 주는 코드와 실제 동작이 따로 작성됨

```ts
// algoCode.ts의 설명 코드 — "밀어내기"
while (j >= 0 && arr[j] > key) { arr[j + 1] = arr[j]; j--; }

// 실제 시각화(insertionSort.ts) — "교환"
[a[j], a[j - 1]] = [a[j - 1], a[j]];
```

설명 코드와 시각화가 서로를 모르기 때문에 어긋나도 알 수 없다.

### 1-7. 테스트가 없음

테스트 파일이 하나도 없어서 아래 버그들이 그대로 남아 있었다.

## 2. 실제로 드러났던 버그·문제

### 성능

| 문제 | 원인 |
|---|---|
| 1,000개 버블 정렬에서 메모리 3~4GB 이상 | 1-1. 스냅샷 75만 개 × 1,000개 참조 |
| 재생 버튼을 누르면 화면이 멈춤 (1,000개: 퀵 0.2초, 버블 7.4초) | 1-2. 메인 스레드에서 전체 단계를 동기 계산 |
| 16배속을 못 따라감 (100개도 초당 44~70단계, 1,000개는 15~27단계) | 1-2, 1-3. 단계마다 전체 리렌더 + DOM 막대 |
| 비교 모드 1,000개에서 단계당 약 400ms (개발 모드) | 1-3. DOM 막대 2,000개 갱신 |
| 병합·기수·계수 정렬의 배치 단계가 O(n²) | 원소 하나 놓을 때마다 `findIndex`로 배열 전체 검색 |

### 정확성

| 문제 | 원인 |
|---|---|
| **하이라이트가 한 단계 어긋남** | 화면 배열은 `steps[k].array`인데 하이라이트는 `stepIndex`가 k+1로 오른 뒤의 `steps[k+1].compare`. "다음에 비교할 막대"에 색이 칠해짐 |
| 셸 정렬이 끝나지 않음 | 사용자가 넣은 간격에 1이 없으면 정렬이 덜 된 채 종료 |
| 기수 정렬이 음수에서 깨짐 | `Math.floor(value / exp) % 10`이 음수 → `count[-3]` 같은 음수 인덱스 |
| 보고 정렬이 말없이 실패 | 5,000번 섞고 멈추지만 "미완료" 표시가 없음 |
| 계수 정렬이 실제 계수 정렬이 아님 | 세는 단계는 `compare: [i, i]`로 흉내만 내고, 배치는 "같은 값 찾아 교환"이라 안정 정렬도 아님 |
| "실행 시간"이 의미 없음 | `performance.now()`로 잰 재생 시간 = 사실상 `단계 수 × 지연`. 알고리즘이 아니라 애니메이션 길이를 잼 |

### 입력·상태

| 문제 | 원인 |
|---|---|
| 입력 검증 없음 | `parseInt`만 함. 음수·소수가 들어가고, 1,000개 제한을 우회하며, 큰 값은 계수 정렬에서 `new Array(max - min + 1)`로 거대한 배열을 만듦 |
| 직접 만든 배열이 랜덤 배열로 덮어써짐 | URL이 바뀔 때마다 `size`와 배열 길이를 비교해 다시 생성. 1개짜리 배열은 size가 2로 보정돼 랜덤 배열로 바뀜. 커스텀 값은 URL에 저장되지 않아 공유도 안 됨 |
| 비교 모드에서 같은 알고리즘을 옵션만 바꿔 비교할 수 없음 | 1-4. 옵션 상태가 하나뿐 |

### 사용성

| 문제 | 원인 |
|---|---|
| 일시정지가 없음 ("중단하기"는 처음부터 다시) | 중단 시 `steps`를 비움 |
| 한 단계 뒤로·진행바 이동이 없음 | 1-1. 스냅샷 모델에서는 되돌릴 방법이 없음 |
| 1,000개 버블 정렬을 끝까지 보는 데 이론상 약 78분 | 1-2. 최고 16배속 = 초당 160단계 |

## 4. 성능 측정

예전(`35db39f`)과 지금을 버블·퀵·병합으로 비교했다. 입력은 두 버전 모두 같은 seed로 만든 무작위 순열. 전체 표와 측정 조건은 [performance.md](./performance.md).

### 4-1. Node: 계산 시간·메모리 (정렬 기록 함수만)

| 1,000개 | 계산 시간 (예전 → 지금) | 결과 메모리 (예전 → 지금) |
|---|---|---|
| 버블 | **26초 후 메모리 부족** → 66.8ms | 4GB 초과 → 12.1MB |
| 퀵 | 135.7ms → 5.0ms (27배) | 143.1MB → 0.39MB (366배) |
| 병합 | 85.3ms → 4.9ms (17배) | 134.0MB → 0.33MB (405배) |

단계당 메모리가 예전은 약 4.2KB(배열 n개 복사), 지금은 16바이트(int32 4개)로 고정이라 크기가 커질수록 차이가 벌어진다.

### 4-2. 브라우저: 실제 앱 (Chrome, 프로덕션 빌드, 16배속)

| 1,000개 | 클릭 후 멈춤 | 초당 단계 (목표 160) | 프레임 간격 평균 / 최악 |
|---|---|---|---|
| 버블 | **7,478ms** → 8ms | 16 → 160 | 88 / 367ms → 19 / 83ms |
| 퀵 | 182ms → 8ms | 26 → 160 | 57 / 200ms → 18 / 83ms |
| 병합 | 258ms → 12ms | 27 → 160 | 56 / 100ms → 18 / 83ms |
| 비교 모드 퀵 vs 병합 | 234ms → 6ms | 15 → 160 | 36 / 100ms → 18 / 67ms |

- 지금 버전은 최고 배속(1024배)에서도 1,000개 단일·비교 모드 모두 초당 약 1만 단계를 60fps로 재생한다. 예전 최고 속도 대비 처리량 약 400~650배.
- 예전 버블 1,000개는 Chrome에서 탭이 죽지는 않았지만 힙 약 3GB를 쓰고 7.4초 동안 멈췄다. Node에서는 4GB를 넘어 실패.

### 4-3. 나빠진 점

- 100개에서는 재생 시작까지 걸리는 시간이 예전 27~41ms → 지금 65~88ms로 늘었다. 워커를 띄우는 비용(약 50ms)이다. 1,000개에서는 예전(0.2~7.6초)보다 빠르다.
