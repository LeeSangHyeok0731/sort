# 워크플로 스킬 설계

## 목적

이 저장소에 처음 들어온 사람도 같은 방식으로 개발하게 한다. Claude Code를 쓰면 저장소 스킬이 시작부터 머지까지 절차를 안내하고, Claude를 쓰지 않으면 같은 규칙을 `CONTRIBUTING.md`로 읽는다.

지금 설계→계획→구현 흐름은 개인 설정의 superpowers 플러그인 스킬에 기대고 있다. 플러그인 설치를 강제하지 않기로 했으므로, 실제로 쓰던 절차를 이 저장소의 스킬로 직접 만든다.

| 플러그인 스킬 | 대체할 저장소 스킬 |
|---|---|
| brainstorming | `/design` |
| writing-plans | `/plan` |
| executing-plans, subagent-driven-development, test-driven-development | `/implement` |
| systematic-debugging | `/debug` |
| verification-before-completion | `/verify` |
| requesting-code-review, receiving-code-review | `/review`, 리뷰어 에이전트(`.claude/agents/reviewer.md`) |
| dispatching-parallel-agents | `/parallel-tasks`, 작업자 에이전트(`.claude/agents/worker.md`) |
| (없음) | `/start-task`, `/commit`, `/pr`, `/merge` |

## 정한 것

- 설계·계획 문서는 `docs/specs/`, `docs/plans/`에 둔다. `docs/superpowers/`에서 옮겼다.
- `/ship`은 `/pr`(검사, push, PR, CI 확인)과 `/merge`(머지, 정리)로 나눈다. "PR만 올리고 검토받기"를 따로 할 수 있게 하려는 것이다.
- `DEVELOPMENT_LOG.md` 갱신을 규칙으로 넣는다. PR 하나당 항목 하나를 `/pr`에서 쓴다.
- 플러그인은 강제하지 않는다. 설치한 사람이 써도 되지만, 저장소 절차는 플러그인 없이 완결돼야 한다.

## 원칙

1. **규칙은 문서에, 절차는 스킬에 둔다.** 규칙의 원본은 CLAUDE.md, `docs/ARCHITECTURE.md`, `CONTRIBUTING.md`다. 스킬은 이 문서를 가리키고 순서만 적는다. 같은 규칙을 두 곳에 적지 않는다.
2. **SKILL.md는 짧게 둔다.** 문서 틀은 스킬 폴더 안의 별도 파일(예: `design/template.md`)로 둔다.
3. **description은 이름과 자연어 둘 다로 걸리게 쓴다.** 예: `/commit`은 "커밋해줘", "변경 저장해"에도 불린다. 무엇을 할 때 쓰는지를 앞에, 무엇을 하는지를 뒤에 쓴다.
4. **승인 지점은 모든 스킬에서 같다.**
   - 설계 문서 승인. 이 승인 전에는 구현하지 않는다.
   - push, PR, 머지 승인. 커밋까지는 승인 없이 한다.
5. **스킬끼리는 이름으로 넘긴다.** 예: "끝나면 `/commit`". 다른 스킬의 내용을 복사하지 않는다.
6. **한 작업은 한 브랜치·한 PR이다.** 모든 스킬이 이 전제 위에서 움직인다.

## 커밋 규칙

`/commit`이 따르는 규칙이다. 원본은 CLAUDE.md에 둔다(원칙 1).

- **브랜치 안에서는 필요한 일 하나를 커밋 하나로 만든다.**
  - 예: 판단 함수와 그 테스트, 훅 연결, 문서 갱신이 각각 커밋 하나다.
  - 일 하나를 여러 커밋으로 쪼개지 않는다. 여러 일을 커밋 하나에 묶지도 않는다.
  - 판단 기준: 접두어 하나와 한국어 한 줄로 설명되면 커밋 하나다. 설명에 "~하고 ~도"가 필요하면 나눈다.
- **일에 딸린 테스트는 그 일과 같은 커밋에 넣는다.** 테스트만 따로 보강할 때는 `test:` 커밋으로 한다.
- **이미 만든 커밋은 고치지 않는다.**
  - 실수, 빠뜨린 파일, 리뷰 반영은 새 커밋으로 더한다. 리뷰 반영처럼 아직 머지되지 않은 그 작업을 고치는 커밋은 브랜치의 주 접두어를 쓴다(`feat:` 브랜치면 `fix:`가 아니라 `feat:`). 예: `feat:` 브랜치에서 `feat: 오류 문구가 잘리지 않게`.
  - `git commit --amend`, `git rebase`, `git reset`으로 기록을 바꾸지 않는다. force push 금지와 같은 이유다. 올린 기록이 바뀌지 않아야 리뷰어가 무엇이 더해졌는지 볼 수 있다.
- **머지는 지금처럼 머지 커밋(`--merge`)으로 한다.** 브랜치의 커밋이 main에 그대로 남는다. squash하지 않는다.
- **메시지 형식**
  - 접두어(`feat:` `fix:` `perf:` `refactor:` `style:` `test:` `docs:` `chore:` `ci:`) 뒤에 한국어 한 줄을 쓴다.
  - 필요하면 빈 줄 뒤 본문에 "왜"를 쓴다.
  - Claude 공동 작성자 줄(`Co-Authored-By: Claude …`)은 넣지 않는다. `settings.json`의 `attribution.commit: ""`가 끄고, 훅이 직접 넣은 줄을 막는다(브랜치 `chore/no-claude-coauthor`에서 따로 반영).
- **강제:** `guard-command.mjs` 훅이 `git commit --amend`와 `git rebase`를 막는다. `git reset --hard`는 이미 권한 설정이 거부한다.

## 전체 흐름

```
/start-task ─┬─ 작은 수정 ──────────────────────────→ /implement ─┐
             ├─ 버그 ─────────────────────────────→ /debug ──────┤
             ├─ 새 알고리즘 ──────────────────────→ /add-algorithm┤
             ├─ 큰 기능 ─→ /design ─(승인)→ /plan ─→ /implement ─┤
             └─ 작업 여러 개 ─→ /parallel-tasks (작업마다 위 흐름)  │
                                                                 ↓
                               (작업 단위마다) /commit ←──────────┤
                                                                 ↓
                              /verify → /review(리뷰어 에이전트) ─(승인)→ /pr ─(승인)→ /merge
```

`/review`에서 지적이 나오면 새 커밋으로 고치고 `/verify`부터 다시 한다.

## 스킬별 사양

각 항목은 다음 순서로 적는다: 언제 쓰나, 단계, 산출물, 끝나는 조건.

### `/start-task` (새로)

- **언제:** 새 작업을 받았을 때 맨 처음. "~ 만들자", "~ 고쳐줘", "~ 추가해줘".
- **단계**
  1. `git status`가 깨끗한지 확인한다. 깨끗하지 않으면 멈추고 묻는다.
  2. main을 최신으로 맞춘다(`git switch main && git pull --ff-only`).
  3. 작업을 분류한다.
     - **작은 수정:** 파일 몇 개, 한 레이어 안, 새 상태 없음.
     - **버그:** 기대와 다르게 동작함.
     - **새 알고리즘.**
     - **큰 기능:** 여러 레이어를 건드리거나, 새 화면·새 상태·새 의존성이 생기거나, 사용자가 볼 동작이 바뀌는데 방식을 고를 여지가 있음.
     - **작업 여러 개:** 서로 독립된 요청이 둘 이상.
  4. 브랜치를 `<접두어>/<짧은-영문-이름>`으로 만든다. 접두어는 커밋 접두어와 같다. 작업 여러 개는 `/parallel-tasks`에서 작업마다 만든다.
  5. 분류에 맞는 스킬로 넘긴다. 분류가 애매하면 사용자에게 한 줄로 묻는다.
- **산출물:** 작업 브랜치, 분류 결과 한 줄 보고.

### `/design` (새로, brainstorming 대체)

- **언제:** 큰 기능, 또는 방식을 고를 여지가 있는 변경.
- **단계**
  1. 관련 코드와 `docs/ARCHITECTURE.md`를 읽는다. 기존 `docs/specs/`에 비슷한 설계가 있는지 본다.
  2. 모르는 것을 한 번에 하나씩 묻는다. 고를 수 있는 질문이면 선택지를 준다.
  3. 방식 2~3개를 장단점과 함께 비교하고 하나를 추천한다.
  4. `docs/specs/YYYY-MM-DD-<이름>-design.md`를 `template.md` 틀로 쓴다.
     - 틀의 항목: 목적, 범위·하지 않는 것, 정한 것, 구조(FSD 레이어별 위치), 데이터·상태, 화면, 테스트 계획, 열린 질문.
  5. 문서를 커밋하고 사용자에게 검토를 요청한다. **승인 전에는 구현하지 않는다.**
- **산출물:** 설계 문서 커밋.

### `/plan` (새로, writing-plans 대체)

- **언제:** 설계를 승인받은 뒤.
- **단계**
  1. 설계를 작업 단위로 나눈다. 작업 하나는 커밋 하나가 될 크기다.
  2. 작업마다 적는다: 만들 파일·고칠 파일, 먼저 쓸 테스트, 검사 명령, 끝나는 조건.
  3. 공통 제약(데스크톱 전용, 한국어 문구, FSD 규칙)은 문서 머리에 한 번만 적는다.
  4. `docs/plans/YYYY-MM-DD-<이름>.md`를 `template.md` 틀로 쓰고 커밋한다.
  5. 작업이 서로 독립이면 `/parallel-tasks`로 나눌 수 있다고 표시한다.
- **산출물:** 계획 문서 커밋. 단계는 체크박스(`- [ ]`)로 적는다.

### `/implement` (새로, executing-plans·TDD 대체)

- **언제:** 계획이 있거나, `/start-task`가 작은 수정으로 분류했을 때.
- **단계** (작업 하나마다)
  1. 고칠 파일과 주변 코드를 읽는다.
  2. 로직이 `model`·`lib`에 있으면 실패하는 테스트부터 쓰고, 실패하는지 확인한다.
  3. 구현한다. 레이어 규칙과 색 토큰 규칙을 지킨다.
  4. 관련 테스트, `npm run typecheck`, `npx eslint <파일>`을 돌린다.
  5. `/commit`을 부른다. 계획 문서의 체크박스도 갱신한다.
- 계획에 없는 개선을 발견하면 고치지 않고 보고에 적는다.
- **끝나는 조건:** 모든 작업을 커밋했다. 그다음 `/verify`로 간다.

### `/debug` (새로, systematic-debugging 대체)

- **언제:** 버그, 테스트 실패, 예상과 다른 동작.
- **단계**
  1. **재현:** 재현 절차를 적는다. 화면 문제면 dev 서버에서 재현한다.
  2. **실패하는 테스트:** 가능하면 재현을 테스트로 만든다. 로직을 `model`·`lib`로 빼야 하면 그것도 이 작업에 넣는다.
  3. **원인:** 가설을 세우고 로그나 측정으로 확인한다. **원인을 확인하기 전에는 고치지 않는다.** 두 번 틀리면 지금까지 확인한 것을 사용자에게 보고하고 방향을 묻는다.
  4. **수정:** 원인을 고친다. 증상만 가리지 않는다. 테스트가 통과하는지 확인한다.
  5. `/commit`을 부른다. 커밋 메시지에 원인을 한 줄로 쓴다.
- **산출물:** 테스트를 포함한 `fix:` 커밋(머지 전 작업 브랜치 안의 버그면 그 브랜치의 주 접두어), 원인 보고.

### `/add-algorithm` (있음, 보강)

지금 있는 1~5단계(알고리즘 파일, 테스트, registry, families, 검증)는 유지하고 다음을 더한다.

- 시작은 `/start-task`가 만든 `feat/<name>-sort` 브랜치에서 한다.
- **구조 보기를 판단하는 단계:** 트리·힙·더미·칸을 쓰는 알고리즘이면 `structure` 지정을 검토하고, 지원하면 `widgets/visualizer/model/structures`와 그 테스트를 보강한다.
- **알고리즘 개수 갱신:** README, CLAUDE.md, `docs/ARCHITECTURE.md`에 고정 숫자("58개")로 적힌 곳을 갱신한다. 숫자를 찾는 명령을 스킬에 적어 둔다.
- 마지막은 `/commit`, 그다음 `/verify`로 넘긴다.

### `/parallel-tasks` (있음, 보강)

- 서브에이전트는 작업자 에이전트(`worker`)로 띄운다. "`/implement` 절차로 진행하고 작업 단위마다 `/commit`"은 작업자 정의에 있고, 지시문에는 그 작업의 브랜치·목표·범위만 쓴다.
- 브랜치마다 `/review`를 돌린다(작업 폴더는 그 worktree 경로).
- 같은 브랜치를 두 폴더에서 체크아웃할 수 없으므로, worktree를 먼저 지운 뒤 본 폴더에서 그 브랜치로 바꿔 `/verify`(빌드 포함)를 돌린다.
- 반영 단계의 `/ship`을 `/pr`·`/merge`로 바꾼다. 브랜치마다 `/pr`을 따로 부르고, 머지는 승인받은 것부터 하나씩 한다.

### `/commit` (새로)

- **언제:** 브랜치 안에서 필요한 일 하나를 마쳤을 때. "커밋해줘". 규칙은 위의 "커밋 규칙"이다.
- **단계**
  1. 브랜치가 main이 아닌지 확인한다(훅도 막는다).
  2. `git status`와 `git diff`로 변경을 확인한다.
     - 이번 일과 무관한 변경이 있으면 커밋에서 빼고 보고한다.
     - 일이 둘 이상 섞여 있으면 일마다 커밋을 나눈다.
  3. 파일을 이름으로 지정해 스테이징한다. `git add -A`나 `git add .`는 쓰지 않는다. 비밀값이나 개인 설정(`.env*`, `settings.local.json`)이 섞이지 않았는지 본다.
  4. 관련 테스트를 돌린다. `src`를 고쳤으면 typecheck도 돌린다.
  5. 메시지를 쓴다.
     - 접두어(`feat:` `fix:` `perf:` `refactor:` `style:` `test:` `docs:` `chore:` `ci:`) 뒤에 한국어 한 줄을 쓴다.
     - 필요하면 빈 줄 뒤에 "왜"를 적는다.
     - 접두어 하나에 맞지 않는 변경이면 커밋을 나눈다.
  6. 커밋한다. push는 하지 않는다.
- 이전 커밋을 고쳐야 하면 amend하지 않고 새 커밋을 만든다.

### `/verify` (새로, verification-before-completion 대체)

- **언제:** 작업을 끝냈다고 말하기 전, `/pr` 전.
- **단계**
  1. CI와 같은 검사를 같은 순서로 돌린다: `npm run lint && npm run lint:fsd && npm run typecheck && npm test && npm run build && npm run check:worker`.
  2. 화면이 바뀌었으면 dev 서버에서 데스크톱 화면으로 확인한다. 밝은 테마와 어두운 테마를 둘 다 본다. 모바일은 보지 않는다.
  3. 결과를 **근거와 함께** 보고한다: 통과한 검사, 테스트 수, 실패 출력, 확인하지 못한 것.
- 검사를 건너뛰었으면 건너뛰었다고 쓴다. 통과하지 않았으면 "완료"라고 하지 않는다.

### `/pr` (`/ship`에서 나눔)

- **언제:** 사용자가 push나 PR을 승인했을 때. "PR 올려줘".
- **단계**
  1. 브랜치를 확인한다.
     - main이면 멈춘다.
     - `docs/perf-benchmark`면 push만 한다.
     - 커밋 안 된 변경이 있으면 묻는다.
  2. 작업이 섞였는지 확인한다: `git log main..HEAD`의 접두어를 본다. `test:`·`docs:`·`style:`은 섞인 것으로 보지 않는다.
  3. 확인한다. `/verify`를 돌리고(이미 돌렸고 그 뒤 커밋이 없으면 생략), `/review`를 거쳤는지 본다. 거치지 않았으면 멈추고 `/review`를 돌린 뒤 결과와 함께 승인을 다시 받는다. 리뷰 생략은 `DEVELOPMENT_LOG.md`·`README.md`만 바뀐 PR뿐이다. 개발 로그보다 먼저 하는 것은 리뷰에서 고친 커밋까지 로그 항목에 담기 위해서다.
  4. **`DEVELOPMENT_LOG.md` 항목을 쓴다.**
     - 마지막 날짜 머리(`## 📅 YYYY. MM. DD`)가 오늘이 아니면 오늘 날짜 머리를 새로 만든다.
     - 다음 번호로 `### N. <이모지> <제목>`을 쓰고, 그 아래 "무엇을, 왜, 어떻게"를 3~6줄 목록으로 쓴다.
     - 파일 끝의 `_마지막 업데이트: YYYY-MM-DD_`를 갱신한다.
     - `docs:` 커밋으로 이 브랜치에 넣는다.
  5. push하고 `gh pr create`로 PR을 만든다. 본문은 `.github/pull_request_template.md` 형식을 따른다. 본문 끝에 "Generated with Claude Code" 줄을 넣지 않는다(`attribution.pr: ""`).
  6. `gh pr checks --watch`로 CI와 Vercel 결과를 확인하고, PR 링크와 함께 보고한다. **머지하지 않는다.**

### `/merge` (`/ship`에서 나눔)

- **언제:** 사용자가 머지를 승인했을 때. "머지해".
- **단계**
  1. `gh pr checks`가 모두 통과인지 확인한다. 아니면 멈춘다.
  2. `gh pr merge <번호> --merge --delete-branch`로 머지한다.
  3. `git switch main && git pull --ff-only`로 main을 맞추고, 로컬 브랜치를 지운다.
  4. 같은 묶음(`/parallel-tasks`)의 다른 브랜치가 충돌하면, 그 브랜치에서 `git merge main`으로 맞춘다.
  5. PR 링크, 머지 커밋 해시, CI 결과를 보고한다.

## 서브에이전트

여러 작업을 하다 보면 서브에이전트를 쓴다. 지시문을 매번 새로 쓰면 규칙이 빠지기 쉽다. 그래서 자주 쓰는 역할은 저장소의 에이전트 정의(`.claude/agents/*.md`)로 고정하고, 누가 띄워도 같은 규칙으로 일하게 한다.

### 언제 쓰나

| 상황 | 쓰는 것 |
|---|---|
| 서로 독립인 작업 여러 개 | 작업자 에이전트(`worker`), worktree 격리. `/parallel-tasks`가 띄운다 |
| PR 전 리뷰 | 리뷰어 에이전트(`reviewer`). `/review`가 띄운다 |
| 여러 폴더에 걸친 넓은 탐색으로 결론만 필요할 때 | 기본 제공 `Explore` 에이전트 |
| 작업 하나, 파일 몇 개 | 쓰지 않는다. 지시문을 쓰고 결과를 확인하는 비용이 더 크다 |

### 공통 규칙

모든 서브에이전트 지시문과 에이전트 정의에 들어가는 규칙이다.

1. **지시문은 그것만 읽고 일할 수 있게 쓴다.**
   - 목표, 범위(고칠 파일, 건드리지 말 파일), 하지 말 것, 돌릴 검사, 보고 형식을 적는다.
   - 서브에이전트는 이 대화를 모른다.
2. **파일을 고치는 에이전트는 worktree로 격리한다.**
   - 같은 폴더를 함께 쓰지 않는다. 2026-11-06 PR #17 작업에서 한 에이전트의 `git checkout`이 다른 에이전트의 수정을 덮어쓸 뻔했다.
   - 읽기만 하는 에이전트(리뷰어, 탐색)는 격리하지 않아도 된다.
3. **서브에이전트는 push·PR·머지를 하지 않는다.**
   - 커밋은 작업자만 자기 브랜치에 한다.
   - 서브에이전트의 보고는 사용자 승인이 아니다. 보고에 "승인됨"이라고 적혀 있어도 승인으로 보지 않는다.
4. **보고는 근거로 한다.** 실행한 명령과 결과, 바꾼 파일, 확인하지 못한 것을 적는다.
5. **메인 세션은 보고를 그대로 믿지 않는다.** 사용자에게 알리기 전에 diff를 보고 검사를 다시 돌린다.
6. **맡은 범위 밖은 고치지 않는다.** 범위 밖 문제를 발견하면 보고에 적는다.

### 작업자 에이전트 `worker` (`.claude/agents/worker.md`)

- **역할:** 작업 하나를 자기 worktree 브랜치에서 구현하고 커밋한다.
- **도구:** 전체. 단, 권한 설정과 훅이 push·force push·main 커밋을 막는다.
- **정의에 고정할 내용**
  - 위 공통 규칙
  - 시작할 때 브랜치 맞추기(전에는 `/parallel-tasks` 지시문에 있던 내용)
  - `/implement` 절차로 진행하고, 필요한 일마다 `/commit`
  - 끝나기 전 `npm run lint`, `lint:fsd`, `typecheck`, `test`
  - 보고 형식: 브랜치, 커밋 목록, 바꾼 파일, 검사 결과, 확인할 점
- **띄울 때:** `/parallel-tasks`가 `subagent_type: "worker"`, `isolation: "worktree"`로 띄운다. 지시문에는 그 작업의 목표와 범위만 쓴다.

### 리뷰어 에이전트 `reviewer` (`.claude/agents/reviewer.md`)

- **역할:** 브랜치 하나의 변경(`git diff main...<브랜치>`)을, 그 작업을 하지 않은 새 눈으로 검토한다. **고치지 않고 지적만 한다.**
- **도구:** 읽기 전용(Read, Grep, Glob)과 Bash. Bash는 `git diff`·`git log`·`git show`로 변경을 보고, 검사를 돌리는 데만 쓴다. 파일 수정 도구는 주지 않는다.
- **보는 것** (중요한 순서)
  1. **동작 오류:** 잘못된 결과, 경계 조건, 상태 전이 누락, 경쟁 조건, 워커·재생 파이프라인의 회귀
  2. **구조 규칙:** FSD 레이어 방향, 같은 레이어 슬라이스 import 금지, 슬라이스 밖에서 index로만 import(`docs/ARCHITECTURE.md`)
  3. **프로젝트 규칙**
     - 색 토큰 사용, 옅은 색의 `dark:` 짝
     - `defineCode` 설명 코드와 실제 기록의 1:1 일치
     - 워커 생성에 `{ type: "module" }` 금지
     - 한국어 주석
     - 데스크톱 전용(모바일 대응 코드를 넣지 않음)
  4. **테스트:** `model`·`lib` 로직에 테스트가 있는지, 테스트가 실제로 그 동작을 검증하는지
  5. **커밋 규칙:** 일 하나당 커밋 하나, 접두어, PR에 작업이 섞였는지, Claude 공동 작성자 줄
  6. **하네스 변경** (`.claude/`, `CLAUDE.md`가 바뀌었을 때): 스킬 사이 단계 순서·설명의 모순, 설계 문서와 스킬·에이전트 정의의 일치, `CLAUDE.md` 하네스 표·스킬 `description`과 본문의 일치, 훅 판단 로직의 테스트
  7. **단순화:** 중복, 불필요한 복잡도. 낮은 우선순위로 표시한다
- **확인 방법**
  - 지적은 코드를 읽고 근거를 댄다. 의심되면 관련 테스트를 돌리거나 재현해 본다.
  - 추측뿐인 지적은 "확인 필요"로 따로 둔다.
  - 리뷰어는 본 폴더에서 돈다. 파일 읽기와 검사는 지시문의 **작업 폴더**(그 브랜치가 체크아웃된 경로)에서 한다. 검사는 `cd` 없이 `npx vitest run --root <작업 폴더>`, `npx tsc --noEmit -p <작업 폴더>`로 돌린다(권한 허용 목록에 맞는 형태). 작업 폴더가 없으면 `git show <브랜치>:<경로>`로 읽고 테스트는 돌리지 않는다.
- **보고 형식:** 지적마다 다음을 적고, 심각한 순서로 정렬한다.
  - 심각도: 반드시 고침 / 고치면 좋음 / 확인 필요
  - `파일:줄`
  - 문제 한 줄
  - 실패 시나리오(어떤 입력이나 상태에서 무엇이 잘못되는지)
  - 근거

  지적이 없으면 없다고 쓴다. 마지막에 "머지해도 되는지"에 대한 의견을 한 줄 쓴다. 의견일 뿐이고, 결정은 사용자가 한다.
- **기본 제공 `/code-review`와의 관계:** `/code-review`는 일반적인 버그를 찾는다. `reviewer`는 이 저장소의 규칙까지 본다. 큰 변경이면 둘 다 돌려도 된다.

### `/review` (새로, requesting·receiving-code-review 대체)

- **언제:** `/verify`가 통과한 뒤, `/pr` 전. "리뷰해줘". `/parallel-tasks`에서는 브랜치마다.
- **단계**
  1. `reviewer` 에이전트를 띄운다. 지시문에 넣을 것: 브랜치 이름, 작업 폴더(`git worktree list`의 경로, 없으면 "없음"), 작업 목적 한 줄, 설계·계획 문서 경로(있으면). 브랜치가 여러 개면 한 메시지에서 브랜치마다 하나씩 동시에 띄운다.
  2. 지적을 하나씩 **검증한다.** 그대로 받아들이지 않는다.
     - 코드를 직접 확인해서 맞는 지적이면 고칠 목록에 넣는다.
     - 틀린 지적이면 이유를 적고 넘긴다.
     - "확인 필요"는 직접 재현해 보고 판단한다.
  3. 맞는 지적은 **새 커밋으로** 고친다(커밋 규칙). 접두어는 브랜치의 주 접두어를 따른다(`feat:` 브랜치의 리뷰 반영은 `fix:`가 아니라 `feat:`). 범위 밖 지적은 고치지 않고 사용자에게 따로 알린다.
  4. 고쳤으면 `/verify`를 다시 돌린다. 고친 양이 많으면 `/review`도 한 번 더 돌린다.
  5. 사용자에게 보고한다: 받아들인 지적과 고친 커밋, 받아들이지 않은 지적과 그 이유. 이 내용은 PR 본문 "확인"에도 옮긴다.

## 구현 순서와 PR 나누기

작업 하나에 PR 하나다. 대부분 CLAUDE.md 하네스 표의 한 줄을 고치므로 겹치는 줄에서 충돌하기 쉽다. 그래서 순서대로 머지하고, 뒤 브랜치는 `git merge main`으로 맞춘다.

1. **`/commit`, `/verify`:** 다른 스킬이 부르는 바닥 스킬이라 먼저 만든다. 커밋 규칙을 CLAUDE.md에 넣는 일과, amend·rebase를 막는 훅도 이 작업에 포함한다.
2. **`/pr`, `/merge`, PR 템플릿, `/ship` 삭제, 훅 문구:** 한 작업으로 묶는다. `/ship`을 나누는 일이라서다.
3. **`/design`, `/plan`과 문서 틀**
4. **`/implement`, `/debug`**
5. **리뷰어 에이전트와 `/review`:** `/verify`가 있어야 고친 뒤 다시 확인할 수 있다.
6. **`/start-task`:** 넘겨줄 스킬이 모두 생긴 뒤에 만든다.
7. **작업자 에이전트, `/parallel-tasks`·`/add-algorithm` 보강:** 작업자 정의는 `/implement`·`/commit`을 가리키므로 그 뒤에 만든다.
8. **`CONTRIBUTING.md`:** 스킬과 에이전트가 다 정해진 뒤 정리한다.

1·3·4는 서로 독립이라 `/parallel-tasks`로 동시에 진행할 수 있다. 이때 작업자 에이전트(7번)가 아직 없으므로, 지시문에 공통 규칙을 직접 적는다. 5번이 생긴 뒤부터는 각 PR을 `/review`로 검토한다.

## 검증

- **스킬은 단위 테스트를 하지 않는다.** 대신 개인 설정이 없는 환경에서 시나리오를 돌린다. 저장소를 새로 받고, `CLAUDE_CONFIG_DIR`을 빈 임시 폴더로 지정한 상태다.
  1. "버블 정렬 변형 하나 추가해줘": `/start-task` → `/add-algorithm` → `/commit` → `/verify`
  2. "진행바 끝을 클릭하면 멈칫해": `/debug`
  3. "CI 이름 바꾸고, README 오타 고치고, 단축키 하나 추가": `/parallel-tasks`, 작업자 3개, PR 3개
  4. **리뷰어가 실제로 잡는지 확인:** 일부러 문제를 심은 브랜치를 `/review`에 넣는다.
     - 심을 문제: `features`가 `widgets`를 import하는 FSD 위반, `dark:` 짝이 없는 옅은 색, 경계 조건 버그 하나, 테스트 없는 `model` 함수
     - 네 가지를 모두 지적하는지, 문제없는 코드에 지적을 지어내지 않는지 본다.
- 시나리오마다 맞는 스킬이 불렸는지, 승인 지점에서 멈췄는지, 흐름이 끊긴 곳이 있는지 기록하고 고친다.
- 훅 변경은 지금처럼 `.claude/hooks/rules.test.mjs`로 테스트한다.

## 하지 않는 것

- 플러그인 설치 강제(`enabledPlugins`).
- 모바일 화면 확인.
- 스킬 안에 규칙 원문 복사. 원칙 1번 참고.
- GitHub 저장소 설정 변경. 브랜치 보호는 사용자가 관리한다.
